# Slack へ通知するポストの本文を日本語に訳す

## 作業の場所

- ブランチ: `feat/translate-to-japanese`（`origin/main` の 9589e6c から分けた）
- worktree のディレクトリ名: `wt-translate`
- 名前に個人情報（アカウント名、姓名、メールアドレス）が含まれないことを確かめた。

## 目的

製品の仕様 `docs/product-specs/x-post-japanese.md`（略号 XPJA、受け入れ基準 XPJA-1〜XPJA-10）を実装する。
Slack へ投稿するポストの通の本文を、原文（英語）から日本語に訳した文にし、訳せなかったときは原文のまま印を付けて投稿する。
仕様の受け入れ基準はすべて実装する（実装しない基準は無い）。

仕様 XPJA は、費用と秘匿値の前提、XPJA-6、XPJA-7 を、翻訳の手段（所有者の契約の Claude Code）に合わせて改める改訂を受けている。この計画は
改訂後の仕様を引き、仕様の文面は書き写さない。改訂後の仕様は、所有者が 2026-11-10 に承認した（手順 0 の (2)）。

翻訳の手段は、所有者が選んだ「所有者の Mac に入っている Claude Code（`claude` コマンド）を、所有者の契約のログインのまま、
画面なしの形（`claude -p`）で子プロセスとして動かす」方法である。Anthropic の API を鍵で使う方法は選ばれなかった。所有者は
「多少トークンを使っても良い」と言っている。

関係する文書:

- 仕様: `docs/product-specs/x-post-japanese.md`（XPJA）。XPJA は、承認済みの仕様 `docs/product-specs/x-post-to-slack.md`（XPOST）の
  XPOST-1 の「本文の全文」と XPOST-19 の「切り詰める本文」の中身だけを改める。XPOST の基準は、完了した計画
  `docs/exec-plans/completed/2026-11-10-x-post-to-slack.md` が確かめたもので、この計画は書き換えない（XPJA-8 で変わらないことを確かめる）。
- `ARCHITECTURE.md` の「層と責務」「依存の向き」「不変条件」「中核的な原則」。層の分け方と依存の向きは変えず、表の行の中身と不変条件と
  中核的な原則を足す（手順 3）。
- ADR: `docs/adr/0002-layers.md`（層を 4 つに分け、依存の向きを lint で守らせる）。`docs/adr/0001-detect-x-cookies.md` と
  `docs/adr/0003-notified-record.md` は、この機能で変えない。新しく ADR 0004（翻訳の手段）を書く（手順 3）。
- `AGENTS.md` の「コードから推測できない決定」の「費用は無料に限る（有料のサービスや API を使わない）。」の項目を、手順 3 で、手順 0 で
  所有者が決めた文面に改める（案は「判断の記録」の D12）。

この機能に含めないもの: launchd での日次の実行の設定（plist）。手順 2 の確かめでは一時的な LaunchAgent を使い、終わったら外す。

### 利用者に諮る判断（手順 0 で済ませた 3 つ）

この計画で所有者に諮ったのは次の 3 つだけで、ほかの決めは設計の中で決めて「判断の記録」に書いた。3 つとも、本物の `claude` を最初に
呼ぶ（手順 1）前に済ませる決めで、2026-11-10 に所有者の回答を受けて済んだ。

1. `AGENTS.md` の費用の決めを改める文面（D12 の案 A）。所有者が案 A で決定した。`docs/PRODUCT_SENSE.md` の理由の文は、決まった文面に合わせて計画の側で書く（別に諮らない）。
2. 改訂後の仕様 XPJA（費用と秘匿値の前提、XPJA-6、XPJA-7）の承認。所有者が承認した。
3. 所有者の Claude の契約で、上限を超えた分を追加で支払う設定（extra usage）が無効であることの確認（V7）。所有者が確かめ、無効だった。
   有効だったときは、契約全体で無効にするか、翻訳の実行を保留するかを所有者が選ぶ分岐だった（記録として残す）。

### 選択肢を絞る前の確かめ

主な決め（判断の記録の D1〜D17）ごとに、示す案の外に 4 種類の案が無いかを確かめた。各決めの比べた案と選んだ理由は「判断の記録」に書いた。

- 両方を行う案:
  - D4（モデル）: 1 回の訳に Haiku と Sonnet のどちらか 1 つを使う、という二者択一は、同じ単位（1 件のポストの訳）の中で他方を行わない決めに当たる。両立しないとする前提には理由の記載が無い。両方を行う形として「最初に Haiku で訳し、やり直しは Sonnet で訳す」形を確かめ、確かめた害も守る前提との抵触も無いので、この形を採った。
  - D2（`claude` のパスの決め方）: 既定値と起動の引数の両方を持つ形を採った。
  - D6（訳文の検証の置き場）: 手段によらない検証（判定と文面）と、手段に固有の検査（外との接続の、包みの漏れ・JSON の形・認証の種類）の両方を、別の層で行う。
  - D16（認証の確かめ）: 実行の前の確かめ（`claude auth status` の形）と、各呼び出しの出力の確かめ（初めの知らせの項目）の両方を、手順 1 で項目が実在すると確かめたものについて行う。
  - D7（実物の訳を観察する手段）: 試し取得に翻訳を足す案と、訳だけを試す引数を足す案を両方行う形は、試し取得が取得した全件（V1 の実績で 37 件）を訳して契約の使用量と時間を使う害があるので外した。試し取得には本文を出すだけの引数を足す（D17）。
- 前提を変える案: 棚卸しで変えうるとした (c) の `postMessage` の形・入口の終了要求の扱い・lint の塊の書き方・試し取得の出力は変える。(c) の入口の例外の受け止めは、理由があり、変えると秘匿値の漏れの危険が増えるので変えず、翻訳の部品の側で例外を外へ出さない（D14）。(b) の層の分け方を変える案は、ADR 0002 の理由が翻訳にも当てはまり、変えた場合の得を 1 文で示せないので外した。(a) の前提を変える案（API の鍵で訳す、Apple の Translation フレームワークなど別の手段で訳す）は、所有者が選んだ翻訳の手段に反するので除いた（選ばなかった理由は ADR 0004 に書く）。(b) の費用の決めは、所有者の選んだ手段と食い違うので、手順 0 で所有者が文面を決める。
- 既存の実装を変える案: `postMessage` に印を渡す形へ変える（採る。手順 4）。`RunDeps` に翻訳の口を足す（採る。手順 6）。`eslint.config.js` に子プロセスの起動を限る規則を足す（採る。D11）。入口に終了要求の受け止めを足す（採る。D14）。試し取得に本文を出す引数を足す（採る。D17）。
- やらない案: 訳文の検証をしない案は、XPJA-2 を守れないので採らない。launchd の確かめを後に回す案は、確かめた結果で翻訳の手段そのものが使えなくなりうるので採らない（手順 2 を実装の前に置く）。認証の種類を実行のたびに確かめない案は、保存済みの認証が API の課金のものに替わったときに気づけないので採らない（D16）。隔離を確かめられない引数を外して進む案は、所有者の規約・フック・MCP が子で動くと訳でない応答や副作用が起きるので採らない（D3。中断する）。

## 検証（完了の条件）

XPJA の各基準の前提・操作・期待する結果は、引いた仕様の受け入れ基準（所有者が承認した改訂後の文面）のとおりで、ここには
書き写さない。ここに書くのは、どう確かめるか（試験で何を差し替え、何を見るか）である。

自動テストは、手順 4〜7 で書く `node:test` の試験である。翻訳は、手順 6 で `src/app/fakes.ts` に足す翻訳の口の偽物
（決まった訳文を返す、決まった回数だけ失敗する、受け取った本文を残す）で差し替える。翻訳の外との接続（`src/adapters/claude-translator.ts`）の
試験は、本物の `claude` の代わりに、試験が一時ディレクトリに作る偽物の実行ファイル（`#!/bin/sh` のスクリプト。受け取った引数・環境・
標準入力をファイルへ書き、決まった出力を出す、待ち続ける、などを行う）を `claude` のパスとして渡す。CI（Linux）では本物の `claude` を呼ばない。
秘匿値は既存の架空の値（`src/app/fakes.ts` の `FAKE_SECRETS`）を使う。形の検査（D6）は訳の正しさを保証しない。訳の意味が正しいかは、
受け入れ確認の担当の観察（`--try-translate` の出力）と所有者の目（V8）で確かめる。

受け入れ確認の基準は、手順 11 で、受け入れ確認の担当が、所有者の秘匿値（アプリが実行時に読む。担当は読まない）と、本物の X・本物の
Slack・本物の `claude`（所有者の契約のログイン）を使って確かめる。本物の Slack のチャンネルへ 6 通ほど投稿される。記録は
`mktemp -d /tmp/x-dev-rss.XXXX` で作った一時ディレクトリを `--state-dir` で渡して置き（所有者の本物の記録に触れない）、対象のアカウントの
設定は既定のもの（@AnthropicAI だけ）を使う。順序は V3 → XPJA-1 → XPJA-8 → XPJA-3 である（前の実行の記録を次の前提に使う）。
受け入れ確認の担当は Slack の画面を見られないので、Slack に届いた通の中身は所有者が目で確かめる（V8）。担当は、コマンドの出力・
終了コード・記録・`--dry-run --show-text` と `--try-translate` の出力で確かめられることだけを判定する。

**対象のポストの選び方（XPJA-1・XPJA-8・XPJA-3 に共通）**: 投稿する実行の前に、`node src/index.ts --dry-run --show-text` で、投稿されるはずの
ポストの ID と原文を確かめ、その原文を `node src/index.ts --try-translate` に標準入力で渡し、1 行目が「訳した」であることを確かめる
（「訳した」は、判定がそのポストを英語のポストとし、本物の `claude` が検証を通る訳を返したことを示す）。1 行目が「訳さなかった」のポストは
英語のポストでないので、その基準の対象に選ばない。選べなかった実行（対象のポストが条件を満たさないのに投稿した実行）は、その基準の
合格に数えない。受け入れ確認の記録には、選んだポストの ID と、`--try-translate` の 1 行目を、基準ごとに書く。

**自動テストと受け入れ確認の記録を分ける**: 受け入れ確認の基準（XPJA-1・XPJA-3・XPJA-8・V3）の合否は、受け入れ確認の記録の実行だけで
決める。同じ基準の振る舞いを固定した入力で確かめる自動テストは V4 の一部として流し、状態の表の根拠には、受け入れ確認の記録の実行の番号と、

## 判断の記録

- D1 訳すかどうかの判定・守る部分・訳文の検証・印の置き場（手順 4・5・6）: 判定と文面（`src/domain/translation.ts` と `src/domain/message.ts`）に、手段によらない決め（訳すかどうか、守る部分、訳文の検証、印、固定の文面）を置く。外との接続（`src/adapters/claude-translator.ts`）には、`claude` に固有のもの（起動、包み、system prompt、認証の確かめ、終了コードと JSON の形、包みの漏れの検査、子プロセスの管理）を置く。実行の流れ（`src/app/translate.ts`）が、判定 → 翻訳の口 → 検証 → 印の順に組み合わせる。比べた案: (イ) 全部を外との接続に置き、接続が通の本文を返す案は、仕様の決め（日本語のポストは訳さない、守る部分）が `claude` の部品に入り、手段を替えると決めも書き直しになり、試験に子プロセスが要るので採らない。(ウ) 判定を実行の流れに置く案は、ADR 0002 が文面と判定を判定と文面に置いた理由（試験に口の偽物が要らない）がこの判定にも当てはまるので採らない。層の分け方と依存の向きは変えないので、ADR 0002 は直さない。この置き方で、翻訳の手段を替えるときに直すのは、外との接続のファイル・入口の組み立て・`eslint.config.js` の子プロセスの許可の一覧だけになる（`ARCHITECTURE.md` の中核的な原則と ADR 0004 の結果に書く）。
- D2 `claude` の絶対パスの決め方（手順 7）: 既定値 `/opt/homebrew/bin/claude` を入口に 1 か所だけ持ち、起動の引数 `--claude <絶対パス>` で替えられるようにする。相対パスは受け付けない。理由: launchd の既定の PATH に `/opt/homebrew/bin` が無い見込みで、PATH から探す形では日次の実行で見つからない。絶対パスなら PATH の中身で別のコマンドに差し替わることも無い。引数で替えられれば、受け入れ確認で `/usr/bin/false` を渡して翻訳の失敗を本物の X と Slack で起こせる（XPJA-3）。比べた案: PATH から探す案（上の理由で採らない）、環境変数で替える案（子の環境の表と紛れ、launchd の設定にも書く場所が要るので採らない）、秘匿値のファイルに書く案（秘匿値ではないので採らない）。

- D4 モデル（手順 5・6）: 1 回目は Haiku（`--model haiku`）、やり直しの 2 回目は Sonnet（`--model sonnet`）で訳す。理由: ポストの訳は短い文の多い作業で、Haiku は契約の使用量と時間の消費が小さい。1 回目が検証を通らなかったポストだけ、より大きいモデルでやり直すことで、質の低さが原因の失敗を減らせる。比べた案: Haiku だけの案（質が原因の失敗をやり直しても同じ結果になりやすい）、Sonnet だけの案（毎日のすべてのポストで、使用量と時間を Haiku より多く使う）。両方を行う形（1 回目と 2 回目でモデルを替える）に、確かめた害も守る前提との抵触も無いので、この形を採った。モデルは別名（`haiku`・`sonnet`）で指定し、版を固定しない（古い版が使えなくなって訳せなくなるのを避ける。版が変わると訳し方が変わりうることは残る危険）。モデルの選び方は外との接続に閉じ、口の `attempt` には手段によらない意味（2 はやり直しで、より強いやり方を選んでよい）だけを持たせる。
- D5 時間切れとやり直し（手順 5・6）: 時間切れは 120 秒とする。決め方は、手順 1 の測りの Haiku と Sonnet のうち長いほうの 3 倍を 30 秒の倍数に切り上げ、120 秒を下回らない値で、手順 1 の最も長い所要は 4000 文字の Haiku の 13.5 秒（起動から終わりまでの実時間）だったので、3 倍の 40.6 秒を切り上げた 60 秒が下限の 120 秒を下回り、120 秒になった（初めの値は 180 秒だった）。値は外との接続の 1 か所の定数に置く。手順 2 の待ちの上限はこの値から計算する。やり直しは 1 回だけ（仕様 XPJA-3 の「やり直しても失敗する」に合わせる）で、間に 5 秒待つ（既存の `RETRY_DELAYS_MS` の 1 回目と同じ長さだが、D21 で `src/app/translate.ts` の独立の定数にした）。1 件のポストで 2 回とも外との接続の失敗だったとき、または認証の確かめ（D16）が契約のログインを示さなかったときは、同じ実行の後のポストは訳さずに失敗の印を付ける（D21 で、1 回目が `unavailable` なら 2 回目を試さずにすぐ止める形に改めた）。理由: 使用量の上限・未ログイン・コマンドが無いときは後のポストも同じく失敗し、時間切れでは 1 件あたり最大で 2 回分の時間切れを待つので、日次の実行が長引く。検証を通らなかっただけ（訳文の中身の問題）のときは、ポストごとの問題なので止めない。

## 結果と振り返り

### 結果

- 仕様 `docs/product-specs/x-post-japanese.md` の受け入れ基準 XPJA-1〜XPJA-10 と、計画の基準 V1〜V8 は、すべて済になった（不合格・対象外は無い）。確かめ方が受け入れ確認の基準（XPJA-1・XPJA-3・XPJA-8・V3）は、受け入れ確認の記録 `docs/exec-plans/completed/2026-11-10-x-post-japanese.acceptance.md` の実行 1 の結果がすべて合格である。
- 翻訳は、手元の Claude Code を画面なしの子プロセスとして呼び、所有者の契約のログインで行う（ADR 0004）。翻訳の手段は `src/adapters/claude-translator.ts` に閉じ込め、訳文の検証と文面は domain の層に置いた。
- 閉じた時点で、`npm run check`（lint・型・247 件の試験）と `bash scripts/harness/check-docs.sh` が通った（未コミットの変更を含めて確かめた）。
- 残る危険:
  - 形の検査は訳の正しさを保証しない。受け入れ確認では「vault particle」が「バールト粒子」と訳された（発見）。誤訳は「（機械翻訳）」の印で読み手に知らせる。
  - 上限を超えた分の支払いの設定が有効かどうかは本文を送る前に確かめられず、設定を有効にした後の最初の 1 回は防げない（ADR 0004）。
  - launchd の設定を作るときは、終了要求の後の最悪の待ち（約 29 秒）より長い `ExitTimeOut` にする（TD-2）。

### ADR の要否

- 翻訳の手段と子プロセスの隔離の決め（D1〜D3・D13・D16）は ADR 0004 に書き、目録に足した。ほかの判断は、この機能の実装の細部で、理由と比べた案はこの計画の判断の記録に残る。

### 振り返り

- 明確さレビューなどの起動が、フックによる入力の書き換えで自動の判定を通らないことが続いた。次からは、同じ発言の中のレビューの回数の枠を、出し直しの分まで見込んで使う。
- 計画の担当が文字コードの誤りで編集に失敗したまま記録したと報告したことがあった。担当の報告にある編集は、grep で結果を確かめてから次へ進む。
