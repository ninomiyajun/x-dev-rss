# X のポストを取得し、まだ通知していないものを Slack へ投稿する（最初の機能）

## 作業の場所

- ブランチ: `feat/x-post-to-slack`
- worktree のディレクトリ名: `wt-xpost`
- 名前に個人情報（アカウント名、姓名、メールアドレス）が含まれないことを確かめた。

## 目的

承認済みの製品の仕様 `docs/product-specs/x-post-to-slack.md`（略号 XPOST、受け入れ基準 XPOST-1〜XPOST-24）を実装する。仕様は実装レビューの後に XPOST-21 の文と目的の節を改め XPOST-24 を足し、利用者が承認し直した（目録の状態は approved）。
コマンドを 1 回実行すると、設定に書いた X のアカウント（最初は @AnthropicAI）ごとに通常のポストで数えて新しいほうから 20 件の候補を取得し、
まだ通知していないポストを Slack の Incoming Webhook へ投稿し、通知済みの記録を更新して終わる。仕様の受け入れ基準は
すべて実装する（実装しない基準は無い）。

あわせて、上位の文書で「まだ決めていない」とされていた次の事項を、この計画で決める。

- 層の分け方と依存の向き（`ARCHITECTURE.md` の「層と責務」「依存の向き」は未決。`AGENTS.md` の「コードから推測できない決定」の最後の項目）。
- 通知済みの記録の具体的な置き場と形式（仕様は「所有者の Mac の、リポジトリの外の決まった場所」とだけ決めた）。
- 通知の文面の細部、やり直しの間の長さ、投稿の間隔、試験の作り方。

関係する文書:

- `ARCHITECTURE.md` の「層と責務」「依存の向き」（どちらも未決。この計画で書く）、「不変条件」と「中核的な原則」（守る。足す）。
- ADR: `docs/adr/0001-detect-x-cookies.md`（X の Cookie を secretlint で検出する。コードで Cookie の値を扱う名前は
  `authToken`・`ct0` などの、検出の規則に合う名前にする）。ほかに関係する ADR は無い。
- `docs/PRODUCT_SENSE.md` の「作らないもの」の節の末尾の 1 文（通知の文面・件数・再試行は未決とする文）は、仕様で決まったので直す（手順 8）。

この計画の範囲には、worktree に既にある次の未コミットの変更を含める（この機能と同じ変更として PR にする）。

- `.github/workflows/drift-scan.yml` と `.github/workflows/harness-secrets.yml` の Node.js の版を `lts/*` から 26 に固定する変更。
- `docs/harness-log.md` に足した、上の変更の 1 行（「入れた変更」の列は、いまはブランチの名前。PR を作ったら番号に書き換える）。
- 仕様のファイル `docs/product-specs/x-post-to-slack.md` と、目録 `docs/product-specs/README.md` の XPOST の行。

この機能に含めないもの（仕様の「この機能で作らないもの」のとおり）: launchd での自動実行、画像や動画の添付、編集や削除の
反映、記録の古い分の管理。

### 受け取った前提の棚卸し

(a) 変えうる判断として扱わず、守る前提（利用者が個別に選んだ判断と禁止、権限と安全の決まり）:

- X の公式 API を使わない。取得は `@the-convocation/twitter-scraper` の 0.22.3 に、取得用の X のアカウントの Cookie
  （`auth_token` と `ct0`）を渡して行う。
- Slack への投稿は Incoming Webhook だけで行う。
- 秘匿値は `~/.config/x-dev-rss/secrets.env`（変数 `X_USERNAME`・`X_AUTH_TOKEN`・`X_CT0`・`SLACK_WEBHOOK_URL`）からアプリが
  実行時に読み、値をリポジトリ・ログ・出力・エラーの文面・Slack への投稿に出さない。エージェントはこのファイルを読まない。
- 費用は無料に限る。取得用のアカウントが使えなくなっても、別のアカウントへ乗り換えない。
- 仕様の受け入れ基準と、仕様が決めた振る舞い（利用者が承認済み）。
- 自動実行（launchd）はこの機能に含めない。
- 公開のリポジトリなので、個人情報とホームの絶対パスをコミットするファイルに書かない（`AGENTS.md` の「秘匿値と個人情報」）。

### 選択肢を絞る前の確かめ

主な決め（判断の記録の D1〜D6）ごとに、示す案の外に 4 種類の案が無いかを確かめた。結果は次のとおりで、各決めの比べた案と
選んだ理由は「判断の記録」に書いた。

- 両方を行う案: D2（記録の置き場）では、置き場を 2 つ持つ案は、どちらを正とするかが決まらず、食い違ったときに XPOST-2 の
  重複が起きる害があるので外した。D3（記録の形式）では、JSON と追記の形を両方持つ案は、壊れたときの判定（XPOST-13）が
  2 通りになる害があるので外した。D4（対象のアカウントの設定）では、リポジトリのファイルとリポジトリの外のファイルを両方
  読む案は、どちらが効いているかが所有者に分かりにくくなる害があるので外した。D5（取得の方法）では、`getTweets` と
  `getTweetsAndReplies` を両方呼ぶ案は、X への要求が 2 倍になり、取得用のアカウントが制限を受けるおそれが増す害があるので外した。
  両立しないとする前提に理由の無いものは無い（どれも、確かめた害による）。設計の中の二者択一に当たるものは無い。
- 前提を変える案: 棚卸しで変えうるとしたのは (b) の「ビルドしない」と (c) の「`node:test`」で、どちらも変えた場合の得を
  この機能について 1 文で示せないので外した。(a) の前提を変える案は除いた（例: 公式 API を使う案は、利用者の禁止に反する）。
- 既存の実装を変える案: 入口の `src/index.ts` と、その試験を置き換える（採る。手順 7）。ほかに妨げになっている作りは無い
  （コードは入口の 1 ファイルだけ）。
- やらない案: 仕様の受け入れ基準を減らす案は、承認済みの仕様を変えるので採らない。

## 検証（完了の条件）

各基準の前提・操作・期待する結果は、引いた仕様の受け入れ基準のとおりで、ここには書き写さない。ここに書くのは、どう
確かめるか（試験で何を差し替え、何を見るか）である。

自動テストの基準は、手順 3〜7 で書く `node:test` の試験で確かめる。X の取得と Slack への投稿は、手順 6 で定める差し替えの
口（取得の口・投稿の口）に偽物を渡して試す。偽物は、決まったポストの並びを返すか、決まった回数だけ決まった種類の失敗を
返し、受け取った通を順に残す。秘匿値には架空の値（16 進数の並びでない文字列。ADR 0001 の検出の規則に当たらない形。
Webhook の URL は `https://hooks.slack.com/` で始まり、後ろが架空の文字列のもの）を使い、記録とロックは試験ごとに作る
一時ディレクトリに置く。待ちと時刻は差し替えの口（すぐ戻る待ち、決まった時刻）を使い、待った長さだけを確かめる。

受け入れ確認の基準は、手順 11 で、受け入れ確認の担当が、所有者の秘匿値（アプリが実行時に読む。担当は読まない）と、

### XPOST-10 秘匿値をどこにも出さない

- 前提: 4 つの変数に、互いに区別できる架空の値を入れる。偽物の失敗の原文にも、その値を含める。ライブラリの `ApiError` の偽物には、応答のヘッダー（`set-cookie` に架空の Cookie の値）と本文に架空の値を入れる。
- 操作: XPOST-1、3、7、8、9、13、15、18、20 の各場面の試験を動かす。加えて、子のプロセスで、環境変数 `DEBUG=*` を付け、入口の `main` に偽の `fetch`（401 と、架空の値を入れた `set-cookie` を返す）を渡す短いスクリプトを `node -e` で動かす試験と、実行の途中で想定外の例外と、受け止められていない Promise の失敗を起こす試験を置く（D13）。
- 期待する結果: 各場面で、出力（標準出力と標準エラー）、投稿の口が受け取った通、記録のディレクトリの全ファイルの中身に、4 つの架空の値が 1 つも含まれない。`DEBUG=*` の試験では、ライブラリの `debug` の出力が 1 行も出ない。想定外の例外の試験では、決まった 1 行だけが出て、終了コードが 1 になる。
- 確かめ方: 自動テスト

## 判断の記録

- D1 層の分け方（手順 2）: 入口・実行の流れ・判定と文面・外との接続の 4 つに分け、依存の向きを `eslint.config.js` の `no-restricted-imports` で守らせる（V3）。実行の流れは node の組み込みを使わず、待ちと時刻も口を通す（試験で待ちと時刻を差し替えるため）。比べた案: (イ) 入口の 1 ファイルに全部を書く案は、仕様の試験（取得と投稿を差し替えて 23 の基準を確かめる）で差し替えの口が要ることと、取得をほかの無料のサービスへ切り替える可能性（`AGENTS.md` の「コードから推測できない決定」の、凍結のときの提案）に、取得のライブラリの型が全体へ広がって備えられないので採らない。(ロ) 判定と文面を実行の流れに混ぜる 3 つの層の案は、選び方と文面の試験に口の偽物が要るようになり、得が無いので採らない。(ハ) 口の型を `src/domain/` に置き、外との接続が app を一切読み込まない案は、依存の向きが「外との接続 → 判定と文面」の 1 本で済む利点があるが、口の型には秘匿値の束・ロック・待ち・時刻のような実行の流れの都合の型が入り、判定と文面が入出力を持たないという責務の線が崩れるので採らない。代わりに、外との接続が読んでよい app のファイルを `src/app/ports.ts` の 1 つに限る。採る理由: 取得のライブラリの型を `src/adapters/x-scraper.ts` に閉じ込められ、取得の手段を替えるときに直すのがそのファイルと設定だけになる。
- D2 記録の置き場（手順 4）: `$XDG_STATE_HOME/x-dev-rss/`（環境変数が無ければ `~/.local/state/x-dev-rss/`）の `notified.json`。`--state-dir` で替えられる。比べた案: (イ) macOS の慣習の `~/Library/Application Support/x-dev-rss/` は、パスに空白を含み、手で扱う手順（受け入れ確認・調べもの）で引用が要るので採らない。(ロ) 秘匿値と同じ `~/.config/x-dev-rss/` は、設定の置き場に実行のたびに変わる状態を混ぜることになり、秘匿値のファイルと同じディレクトリを毎回書き換えるので採らない。採る理由: 秘匿値の置き場（`~/.config`）と同じ XDG の並びで、状態のための場所であるため。
- D3 記録の形式（手順 4）: JSON の 1 ファイル `{"version": 1, "accounts": {"<小文字のアカウント名>": {"ids": ["<ID>", …]}}}`。アカウントごとに持ち、あるアカウントの項目が無いことを「そのアカウントは初めての実行」とする（XPOST-17 の「一方の記録の有無が他方に影響しない」に合わせる）。初めての実行で取得したポストが 0 件のときも、空の `ids` で項目を作る。書き込みは同じディレクトリの一時ファイルに書いて名前を変える。比べた案: (イ) 1 行に 1 件を追記する形は、途中で切れた最後の行を「壊れている」とするか「無視する」とするかの決めが要り、XPOST-13 の判定が曖昧になるので採らない。(ロ) Node.js の組み込みの SQLite は、受け入れ確認と調べもので手で開いて直す（XPOST-1 の前提を作る）のに道具が要るので採らない。採る理由: 壊れたことを JSON の読み取りと形の確かめで一通りに決められ、手で読める。記録の古い分は消さない（仕様の範囲の外）。

- D5 取得の方法と候補の選び方（手順 3・5）:
  - 取得は、`x-scraper.ts` の 1 か所の定義（見張るエンドポイントの名前 `UserTweets`、呼ぶメソッド `getTweets`、タイムラインの要求の上限 4 回、受け取るポストの上限 200 件、応答の検査）にまとめ、片方だけを替えられない形にする（実装レビューの指摘）。並びの読み方: 受け取ったポストを、判定と文面の集め役（`src/domain/select.ts` の `TimelineCollector`）へ 1 件ずつ渡す。集め役が「固定表示でない通常のポストが 20 件そろった」と言ったら、そのページは読み切り、次のページの要求を `fetch` の包みが X へ送らずに目印の例外で拒んで止める（止まり方「20 件そろった」）。並びが終わったら「並びの終わりまで取得した」。タイムラインの要求が 4 回に達したか、受け取ったポストが 200 件に達したら「上限で止まった」（5 回目の要求は目印の例外で拒む）。候補は、集めたポストから ID の大きい順（`BigInt`）に選ぶので、1 ページの中の並びが順不同でも 20 位以内が欠けない。`getTweetsAndReplies` から `getTweets` に替えた（利用者の決定で返信を通知しなくなったため。返信は並びに入らなくなり、記録もされない）。
  - 数える対象: 投稿者が対象のアカウントの、通常のポスト（返信・リポスト・引用のどれでもないもの）だけ（利用者の決定 2026-11-09）。返信・リポスト・引用は「投稿しないで記録する」対象で、数えない。投稿者が対象のアカウントでないポスト（会話のまとまりに入る他人のポスト）は、数えず、記録もしない（D11）。
  - 順位: 数える対象（固定表示のものを含む）を ID の大きい順（`BigInt` で比べる。D14）に並べた位置。1〜20 位を候補とする。固定表示のポストは、順位を決めてから扱い、20 位以内なら候補、21 位以下なら候補にしない（XPOST-16）。固定表示のポストが 20 位以内にあると、固定表示でない 20 番目のポストは 21 位になり、その回の候補にならない。
  - 記録する範囲: 20 位のポストの ID 以上の ID を持つ、返信・リポスト・引用も、投稿しないで記録する（20 位より古いものは、次の回以降に範囲に入ったときに記録する）。数える対象が 20 件に満たないとき（並びが終わったか、上限で止まったとき）は、受け取った返信・リポスト・引用をすべて範囲に入れる。
  - 初めての実行（記録にアカウントの項目が無い）: 候補のうち順位 1 位だけを投稿し、残りの候補と、記録する範囲の返信・リポスト・引用を、投稿の前に記録する。
  - 漏れのおそれ（XPOST-20）: 記録にアカウントの項目があるときだけ判定する。(a) 止まり方が「並びの終わりまで取得した」なら知らせない。(b) 途中で止めたとき（20 件そろった・上限で止まった）は、取得できた通常のポスト（固定表示を含み、新しいほうから最大 20 件）が、記録に 1 件も無ければ知らせる。上限で止まり 20 件そろわなかったときも同じ判定で、見つかった候補は投稿し、知らせた回は「新しいポストはありません」を送らない（まとめ役の判断の答え 2026-11-10。見つかった通常のポストに記録済みのものがあれば、それより新しいものはすべて取れているので漏れは無い）。記録済みの返信・リポスト・引用は判定に数えない（仕様の文に合わせる。実装レビューの指摘）。

- D6 通知する種類（手順 3）: 利用者の決定（2026-11-09。「通常のポストのみを slack に通知してください。引用ポストも不要です」）により、Slack に通知するのは通常のポスト（返信・リポスト・引用のどれでもない、対象のアカウント自身のポスト）だけにした。返信（相手が自分でも他人でも）・リポスト・引用は通知せず、通知済みとして記録する。これは仕様の XPOST-6（自分への返信と引用を投稿する）から変わる点で、仕様の文面は別の担当が直す。返信の相手を見分ける処理（X の元の項目 `in_reply_to_user_id_str` の読み取り、同じ回の取得での判定、項目が無いときの安全策）は要らなくなったので作らない。通知する種類の規則は `src/domain/post.ts` の1 か所（`isNotifiedKind`）にまとめた。以前の案（返信の相手を見分けて自分への返信を通知する案と、その案 ア〜ウ）は採らない。
- D7 1 通の長さの上限（手順 3・5）: 1 通の `text` の上限を 40,000 文字とし、Slack の口に持たせる。超えるときは本文を切り詰めて「…（長いため途中まで）」を付け、アカウント名・日時・URL は残す。上限との比べは、Slack の口の書き換え（`&` などを `&amp;` などへ）をした後の長さで行う（書き換えで長くなるため）。切り詰めの関数は判定と文面に置き、上限の値と長さの測り方を引数で受け取る。理由: Slack の文書が、メッセージの `text` は 40,000 文字を超えると切り詰められるとしているため（計画の担当の知識による。Incoming Webhook の文書で同じ値かは確かめていない。残る危険として結果と振り返りの節に書いた。値は D16 のとおり 1 か所にある）。
- D8 やり直しと投稿の間隔（手順 6）:
  - X の取得: 一時的な失敗（HTTP 5xx の `ApiError`、`fetch` の `TypeError`、打ち切り、D12 の異常な応答のうち構造の欠け）のときだけ、5 秒、15 秒の間を空けて 2 回までやり直す（1 アカウントの取得の全体をやり直す）。X の 429 はやり直さない（すぐに要求を重ねると、取得用のアカウントが制限を受けるおそれが増すため）。ログインの拒否、対象のアカウントの失敗、そのほかの失敗もやり直さない（XPOST-22）。
  - Slack の投稿: 投稿の口の 2 回目以降の呼び出しの前に、前の呼び出しから 1.1 秒以上を空ける（ポストの通も、まとめの通も同じ）。Slack の文書（docs.slack.dev の rate-limits）が、Incoming Webhook をおおむね 1 秒に 1 通としているため。一時的な失敗のときは、5 秒、15 秒の間を空けて 2 回までやり直す。429 のときは、Retry-After の秒数（無ければ 5 秒）を待ってやり直し、これもやり直しの 2 回に数える。Retry-After が 60 秒を超えるときは、待たずに投稿の失敗（XPOST-8 の扱い。そこで止め、次の実行に回す）とする（手で実行する所有者を長く待たせないため）。
  - 比べた案: 間を空けない案は、通信の切れ目や 429 が続く間にやり直しを使い切るので採らない。もっと長い間（分の単位）は、手で実行する所有者を待たせるので採らない。
  - Slack が受け付けた後に応答だけが失われた（打ち切り・5xx）ときは、やり直すので、同じポストがもう 1 通投稿されうる。利用者はこれを許すと決めた（仕様の XPOST-21 の改めた文。Slack が受け取ったと応答した投稿は 2 回投稿しない）。Webhook には重ねて送ったことを見分ける仕組みが無い。
- D9 ロック（手順 4。実装レビューの指摘で改めた）: 記録のディレクトリに `run.lock` を置く。中身は、プロセスの番号と、そのプロセスの開始時刻（`ps -o lstart= -p <番号>` の出力。`ps` は絶対パス `/bin/ps` で呼び、環境変数として `LC_ALL=C` と `TZ=UTC` だけを渡し、端末と launchd のようにロケールや時間帯の違う実行から読んでも同じ文字列になるようにする）の 2 行。(1) 自分の中身を書いた一意の名前の一時ファイルを作り、`link` で `run.lock` の名前を付ける（取れるのは 1 つだけ）。取れたら読み直して自分の中身であることを確かめる。(2) `EEXIST` のときは中身を読み、番号が 1 以上の整数で、`process.kill(<番号>, 0)` が成功するか `EPERM` で、かつ今のそのプロセスの開始時刻が書かれた開始時刻と一致するときだけ、生きているとする（XPOST-14）。開始時刻が違えば番号の使い回しで、古いとする。開始時刻を `ps` で得られなかったときは、生きているとする（奪わない側に倒す）。時刻の超過だけで奪うことはしない。(3) 古いロックの回収: 古いと読んだ中身から作った名前の回収の印（`run.lock.reclaim.<中身の要約>`）を `link` で取った 1 つだけが、`run.lock` の中身がまだ同じであることを確かめて消し、印を外して (1) を 1 回だけやり直す。印を取れなかった実行は、ほかの実行が動いているとして終わる。`run.lock` を消せるのは、その中身の印を持つ実行だけなので、読んでから消すまでの間に中身は変わらず、3 つ以上が同時に回収しても `run.lock` を取れるのは 1 つだけになる。印を持ったまま止まった実行の印は、印の中身（番号と開始時刻）が古ければ、同じ手順を 1 段深く（印の印で）使って回収する（2 段まで）。外すときは、`run.lock` の中身が自分のものであることを確かめてから消す。比べた案: 古いロックを別の名前へ `rename` してから中身を確かめる前の作りは、3 つが重なると、戻す途中で 3 つ目が作った新しいロックと食い違い、2 つが取れることがあるので採らない。
- D10 失敗の種類と通の文面（手順 3・5）:
  - X の取得の失敗の種類: ログインの拒否（取得用のアカウント。`AuthenticationError`、HTTP 401・403 の `ApiError`）、対象のアカウントを取得できない（F6 の `getProfile` の `Error`。凍結・存在しない・非公開・応答の `errors`）、一時的（D8）、X の 429、異常な応答（D12）、そのほか。ログインの拒否の判定の根拠は F6 のとおりで、X の応答の形は確かめていない（残る危険: X が別の状態の番号で拒んだときは「そのほか」になり、やり直さないことは同じだが、文面が「ログインが拒まれた」にならない）。
  - ポストの通: 1 行目 `@<アカウント>`、2 行目 `<YYYY-MM-DD HH:MM>（日本時間）`、3 行目から本文、最後の行に URL（XPOST-1 の順）。種類の印（引用など）は付けない。
  - まとめの通: 新しいポストが無い旨は「新しいポストはありません（確かめたアカウント: @AnthropicAI、@<Q>）」。取得の失敗は 1 通の中で、アカウントごとに「@<アカウント>: <種類の文>」を並べる（種類の文は「取得用のアカウントのログインが拒まれました」「対象のアカウントが見つからないか、凍結か非公開です」「X が要求を制限しています」「通信に失敗しました」「X の応答が想定と違いました」「取得に失敗しました」）。漏れのおそれは「取得した件数より古いポストが通知されずに漏れたおそれがあります: @<アカウント>」で、複数のアカウントは 1 通に並べる。記録が読めないときと設定が読めないときも、それぞれ 1 文にする。出力の行も同じ文を使い、件数の行は「通知した件数: <数>」。
- D11 種類の判定の重なり（手順 3）: リポストは、ほかの印があっても投稿しない。返信は、引用の印があっても返信として扱う（どちらも投稿しない）。投稿者が対象のアカウントでないポスト（リポストを除く。会話のまとまりに入る他人のポスト）は、投稿も記録も数えることもしない。仕様の XPOST-6 は 1 件ごとに 1 つの種類の場合だけを決めているので、重なったときは、投稿しない側を優先した。
- D12 異常な応答の検出（手順 5）: F7 のとおり、ライブラリの戻り値では区別できないので、`x-scraper.ts` が `Scraper` に渡す `fetch` の包みで、URL のパスが D5 の 1 か所の定義のエンドポイントの名前（`UserTweets`）で終わる要求の応答を `clone()` して JSON として読み、次のどれかなら、その回の取得を異常な応答として失敗にする（ライブラリから返った並びは捨てる）: `data.user.result.timeline.timeline.instructions` が配列でない（応答の `errors` が空でない配列でも無くても）、JSON として読めない。`instructions` が配列のときは、`errors` があっても失敗にしない（X は、正しい `data` に一部の項目の `errors` を付けて返すことがあるため）。`data.user.result` の `__typename` が `UserUnavailable` のときは、対象のアカウントを取得できない失敗にする。`instructions` が無く `errors` も無いもの（構造の欠け）と、JSON として読めないものは一時的、`instructions` が無く `errors` があるものはやり直さない。異常でない応答で、ポストが 0 件のときだけを「ポストが無い」とする。
- D13 入口の環境の整えと、想定外の例外（手順 7）: 入口は、取得のライブラリを含む外との接続の部品を、`process.env.DEBUG` を消した後に動的な `import()` で読み込む（`debug` は読み込まれたときに `DEBUG` を読むため。静的な `import` だと消す前に読み込まれる）。`DEBUG` があったときは、消したことを 1 行で知らせる（値は出さない）。止める案は、所有者の手元の環境に `DEBUG` が残っているだけで動かなくなるので採らない。`process.on("uncaughtException")` と `process.on("unhandledRejection")`、`main` の外側の `try` で想定外の例外を受け止め、「想定外の失敗で止まりました」の決まった 1 行だけを出し、ロックを持っていれば外して、終了コード 1 で終わる（例外の文面は出さない）。環境変数 `NODE_DEBUG` が空でないときは、秘匿値を読む前に、決まった 1 行を出して終了コード 1 で止める（Node.js の `fetch` の記録が、送り先の URL のパス〔Webhook の URL の秘匿の部分〕を出すため。`DEBUG` と違って消しても効き目が読み込みの順に左右されるので、止める側に倒した）。`XDG_STATE_HOME` が絶対パスでなければ無視して既定の場所を使う。
- D14 ID と日時（手順 3）: 並べ替えと比べは、ID を `BigInt` にして行う（10 進数の文字列の長さが違うと、文字列の比べでは順が狂うため）。日時が無いポストは、ID から求める（X の ID の上位の桁が時刻を表す形〔ID を 22 ビット右へずらし、1288834974657 ミリ秒を足す〕）。ID が 10 進数の文字列でないポストがあれば、その回の取得を「そのほか」の失敗にする。比べた案: 日時の無いポストがあれば取得の失敗にする案は、その 1 件のために毎回失敗し続けるので採らない。
- D15 秘匿値の受け渡し（手順 4・6）: 秘匿値の口は、「揃った秘匿値の束」か「足りない変数の名前と、形の違う変数の名前の一覧」を返す。束の型は `src/app/ports.ts` で中身の無い型（印だけを持つ型）として定め、中身は `src/adapters/secrets.ts` の中でだけ読める（実行の流れは束を開けずに、取得と投稿の部品を作る口へ渡す）。必須の変数の一覧と形の確かめは `src/adapters/secrets.ts` に持つ。比べた案: 値の入った辞書を実行の流れへ渡す案は、実行の流れのどこからでも値を出力に混ぜられるので採らない。
- D16 実装の途中で決めたこと（手順 2〜7）:
  - 試験だけが使う偽物の口と架空の秘匿値を `src/app/fakes.ts` に置いた（node の組み込みを使わないので、実行の流れの層の決まりに合う）。アプリのコードからは読み込まない。`ARCHITECTURE.md` の表に書いた。
  - 外との接続の試験は、ファイルを扱うもの（`src/adapters/files.test.ts`）と、外へ通信するもの（`src/adapters/network.test.ts`）の 2 つにまとめた（部品ごとに 1 つずつ置く計画の書き方から外れるが、同じ一時ディレクトリと偽物の fetch の作り方を共有するため）。
  - 試し取得（`--dry-run`）は、取得をやり直さない。これは意図どおりである（V1 で数える要求の回数に、やり直しの分が混ざらないため）。
  - 集め役（`TimelineCollector`）が「20 件そろった」と決めるときは固定表示のポストを除いて数え（固定表示のポストは古くても並びの先頭に来るので、数えると新しいポストが 20 件に届く前に止まるため）、候補を選ぶときの順位付けは固定表示のポストを含めて数える（XPOST-16 の、20 位以内なら候補とする決まりのため）。
  - Slack の 429 で Retry-After が無いときは、5 秒を待つ（D8 のとおり）ことを、投稿の口の結果に 5 秒を入れて表した。
  - 受け止められていない例外の決まった 1 行は標準エラーに、それ以外の行は標準出力に出す。
  - D7 の上限 40,000 文字は、Incoming Webhook の文書で確かめていない（作業担当はネットワークへ要求しない決まりで動いたため）。値は `src/adapters/slack-webhook.ts` の `SLACK_TEXT_LIMIT` の 1 か所で、違えば直す。

- D17 実装レビュー（秘匿値の担当・設計品質の担当・別のモデルの第二レビュー）の指摘で改めたこと（2026-11-10。利用者が直し方を承認）:
  - 秘匿値のファイルは、グループかほかの利用者に読み取りの権限があれば、中身を読まずに止める。読めない（`EACCES`）ときと、無いときを別の文にする（V7）。
  - Slack への `fetch` に `redirect: "error"` を付ける（転送先へ本文を送らないため。V8）。
  - 記録の書き込みは、一時ファイルを `fsync` してから名前を変え、失敗したら一時ファイルを消す（V8）。
  - 記録の読み込みで、小文字にそろえると同じ名前になるアカウントが 2 つあれば、壊れているとする（XPOST-13）。
  - 取得の失敗の分け方: Cookie を渡す段の失敗は「そのほか」、利用者の ID を引く段の素の `Error` は、ライブラリの決まった文（「User is suspended.」「User not found.」「User <名前> does not exist or is private.」）と照らし合わせて一致したときだけ「対象のアカウントを取得できない」にし、ほかは「そのほか」にする（凍結との取り違えを防ぐ）。
  - 依存の向きの lint は、相対パスの深さによらず効く正規表現の形にし、入口が `src/adapters/x-scraper.ts` を静的に読み込むことも禁じる。`run.ts` と `inspect.ts` の最初の段取り（秘匿値 → ロック → 外す）は 1 つの関数にまとめる。
  - 投稿した後に記録の書き込みに失敗したときは、そこで止め、決まった 1 行と Slack への 1 通で知らせて終了コード 1（XPOST-24）。その 1 通には、それまでに集めたほかのアカウントの取得の失敗と漏れのおそれも含める（XPOST-23 のまとめた 1 通と合わせる。再レビューの指摘）。投稿の前の記録の書き込み（投稿しないと決めた ID）に失敗したときも同じ扱いにする。
- D18 再レビュー（秘匿値の担当・設計品質の担当）の指摘で改めたこと（2026-11-10）:
  - 秘匿値のファイルは、権限が所有者だけ（`mode & 0o077` が 0）で、持ち主が実行している利用者であるときだけ読む。合わなければ止める。権限の問題と持ち主の違いは、別の理由と別の 1 行で知らせる（値とパスは出さない）。
  - `X_AUTH_TOKEN` と `X_CT0` は、英数字と `%`・`_`・`-` だけの形に限り、合わなければ形の違う変数として止める（Cookie の文字列に区切りの文字が混ざるのを防ぐ。値は出さない）。
  - 記録の書き込みは、手元の状態を複製して書き、成功したときだけ差し替える（失敗した ID が手元に残らない）。名前の変更の後に置き場のディレクトリを `fsync` する（失敗しても止めない）。
  - lint で、`src/adapters/x-scraper.ts` 以外の外との接続からも、x-scraper を静的に（値として）読み込むことを禁じる（型だけの読み込みは許す）。
  - 残る危険: ロックの持ち主の開始時刻を `ps` で得られないときは、持ち主が生きているとみなすので、持ち主が終わった後も古いロックが残り、実行が「ほかの実行が動いている」で終わり続けうる。番号の使い回しは開始時刻で見分けられ、残るのは `ps` が失敗した場合だけで、macOS では起きにくいため、知らせる仕組みは作らない。

## 結果と振り返り

### 結果

- 仕様 `docs/product-specs/x-post-to-slack.md` の受け入れ基準 XPOST-1〜XPOST-24 と、計画の基準 V1〜V8 は、すべて済になった（不合格・対象外は無い）。確かめ方が受け入れ確認の基準（XPOST-1〜4・XPOST-11・V1）は、受け入れ確認の記録 `docs/exec-plans/completed/2026-11-10-x-post-to-slack.acceptance.md` の、判定に数える実行の最新の結果がすべて合格である。
- 層を 4 つ（入口・実行の流れ・判定と文面・外との接続）に分け、依存の向きを `eslint.config.js` の規則と `src/architecture.test.ts` で守らせた。設計の正本は `ARCHITECTURE.md` に書いた。
- 閉じた時点で、`npm run check`（lint・型・114 件の試験）と `bash scripts/harness/check-docs.sh` が通った（未コミットの変更を含めて確かめた。コミットはまだ無い）。
- 所有者が本物の記録の置き場で初めて実行すると、受け入れ確認では一時ディレクトリの記録を使ったため、XPOST-4 の扱いで最も新しい 1 件がもう一度 Slack へ投稿される（手順 11）。
- 残る危険:
  - 固定表示のポストに印が付くことは、対象のアカウントに固定表示のポストが無いため、本物の応答では確かめておらず、自動の試験だけで確かめている（発見の F11）。
  - Slack の 1 通の上限 40,000 文字は、Incoming Webhook の文書で確かめていない（D7・D16。値は `src/adapters/slack-webhook.ts` の `SLACK_TEXT_LIMIT` の 1 か所）。
  - ロックの持ち主の開始時刻を `ps` で得られないときは、古いロックが残りうる（D18）。

### ADR の要否

- 残す価値のある設計判断のうち、層の分け方（D1）は ADR 0002、通知済みの記録の置き場と形式（D2・D3）は ADR 0003 に書き、目録 `docs/adr/README.md` に足した。
- ほかの判断（D4〜D18）は、この機能の実装の細部で、守る決まりは `ARCHITECTURE.md` の依存の向きと不変条件に書いたので、新しい ADR は書かない。判断の理由と比べた案は、この計画の判断の記録に残る。

### 振り返り

- V1 は、受け入れ確認の担当が X の画面を見られないため、実行 1 では固定表示の印が 0 件で正しいかを決められず、「未確認」になった。計画を閉じる段で、`completed/` の計画では受け入れ確認の基準の最新の結果が合格でないと `bash scripts/harness/check-docs.sh` が失敗にすると分かり、閉じるのを止めた。所有者に対象のアカウントに固定表示のポストがあるかを確かめてもらい、無いと分かったので、受け入れ確認の担当が実行 2 で、アプリを動かし直さずに V1 を判定し直して合格にした。
- 次からは、受け入れ確認の担当が自分で観察できない事実（外のサービスの画面にしか無い状態など）に結果が左右される基準は、計画を書くときに前提として所有者に確かめておくか、確かめる手段を基準に書いておく。
